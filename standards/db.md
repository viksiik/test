# Стандарт: робота з даними

**Навіщо.** Аудит Лаби 2 показав: код, що працює на статичних даних, ламається на справжній БД під
паралельними запитами. Ці правила закривають кожен знайдений клас помилок, а не окремий баг.

| ID    | Правило                                                                                                                                                                                           | Чому                                                                         | Як перевіряється     |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | -------------------- |
| DB-01 | **Жодного check-then-act без блокування.** Якщо рішення «можна/не можна» залежить від прочитаних рядків, ці рядки читаються `FOR UPDATE` у тій самій транзакції, або інваріант тримає constraint. | Між SELECT і INSERT інша транзакція встигає змінити дані (аудит №1).         | C1–C3, `make race`   |
| DB-02 | **Інваріант, що стосується кількох рядків, дублюється в БД** (UNIQUE / частковий індекс / CHECK). Код дає зрозумілу помилку, БД — гарантію.                                                       | Блокування легко забути в новому сценарії; constraint — ні.                  | C3, міграції         |
| DB-03 | **Ідемпотентний запис = `ON CONFLICT DO NOTHING` + перечитування**, а не «спершу SELECT». Повтор з іншим тілом — 409.                                                                             | SELECT-перевірка не бачить незакомічений паралельний запис → 500 (аудит №2). | C4, C5               |
| DB-04 | **Бюджет запитів на кожен список**: кількість SQL не залежить від N. Дані зі звʼязаних таблиць — JOIN у read model адаптера.                                                                      | N+1 непомітний на 3 рядках і вбиває на 300 (аудит №3).                       | Q1, `make n1-report` |
| DB-05 | **Недоступність джерела ≠ 500.** Мережеві/таймаут-помилки → `UnavailableError` → 503 + `Retry-After`.                                                                                             | Клієнт має знати, що запит можна повторити.                                  | F1–F3, `make chaos`  |
| DB-06 | **Повтор транзакції — лише цілком і лише на 40001/40P01**, ≤ 3 спроб з backoff.                                                                                                                   | Повтор частини транзакції або неідемпотентної дії = дубль.                   | R1–R3                |
| DB-07 | **Міграції незмінні** після застосування; зміна схеми — нова міграція.                                                                                                                            | Інакше БД у різних середовищах розходиться.                                  | рев'ю PR             |
| DB-08 | **Конкурентні тести проганяються багато разів** (`make race`, 20×). Один зелений прогін гонки нічого не доводить.                                                                                 | Наївна версія проходила C2/C3 у ~⅔ запусків.                                 | `make race`          |
