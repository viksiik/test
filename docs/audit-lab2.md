Головний висновок: **статика приховала дві з трьох проблем** — сховище в пам'яті виконувало транзакції по черзі,
тож гонок там не могло бути. Їх знайшли лише паралельні запити до справжньої БД.

## Топ-3 зрізані кути / крайові випадки

### 1. Check-then-act без блокування → порушення I1, I2, I3

**Що було:** «порахувати активні → якщо < ліміту, вставити» і «прочитати тікет → якщо `queued`, оновити»
окремими запитами в READ COMMITTED. **Доказ:** 12 паралельних реєстрацій при ліміті 5 →
`201×10, 409×2`; два майстри на одну річ → `200, 200` (9 з 30 запусків).
**Виправлення через стандарт:** `standards/db.md` DB-01 (жодного check-then-act без `FOR UPDATE`) і DB-02
(інваріант дублюється constraint-ом). Код: `lockEventForRegistration` (I3), `findById … FOR UPDATE` (I1),
міграція `002_invariants.sql` — частковий UNIQUE `tickets(volunteer_id) WHERE status='in_repair'` (I2);
порушення індексу → 409 `VOLUNTEER_BUSY`. Рішення і альтернативи — [ADR 0005](../adr/0005-concurrency-locks-and-constraints.md).
**Закріплено:** C1–C3 + `make race` (DB-08: гонку перевіряємо 20 разів, не один).

### 2. Ідемпотентність лише «на щасливому шляху» → 500 і чужий тікет

**Що було:** «знайти за ключем → якщо немає, вставити». Два дефекти:
(а) паралельні повтори з одним ключем не бачать незакомічений запис одне одного → `23505` → **`201, 500×5`**;
(б) **знайдено ще на статиці:** той самий ключ з _іншим_ тілом повертав попередній, чужий тікет зі статусом 200 —
spec цей випадок просто не описувала.
**Виправлення через spec і стандарт:** у spec додано I4-уточнення та **AC7** (повтор з іншим тілом → 409
`IDEMPOTENCY_KEY_REUSED`); DB-03 — запис через `INSERT … ON CONFLICT DO NOTHING` + перечитування переможця.
**Закріплено:** C4, C5; живий збій — клієнт повторює POST після 503 і отримує рівно один тікет ([chaos](../reports/lab2-6-chaos.txt)).

### 3. N+1 у дошці сесії

**Що було:** `queue()` брав список тікетів, а потім для кожного викликав `volunteers.getVolunteer()` —
коректно з погляду меж модулів, але **1 + N запитів**. **Доказ** (`make n1-report`):
1 річ → 3 запити, 10 → 12, 50 → 52 ([до](../reports/lab2-3-n1-before.txt)). Після: **2 запити для будь-якого N**
([після](../reports/lab2-5-n1-after.txt)).
**Виправлення через spec і стандарт:** у spec §1 зафіксовано, що read model, який з'єднує таблиці двох модулів,
живе в адаптері (`TicketStore.listQueue` — один `LEFT JOIN`); DB-04 — бюджет запитів на кожен список.
**Закріплено:** тест Q1 (≤ 2 запити для 1 і для 15 речей).

## Коректність запитів (інші перевірені місця)

Пошук N+1 у решті: `register` — 6 запитів сталої кількості, `claim` — 5, `history` — 1, `/events` — 1. Індекси під
усі `WHERE`: `tickets_event_idx (event_id, created_at)`, `ticket_transitions_ticket_idx`, UNIQUE на ключ і майстра.

## Поведінка на збоях

| Ситуація                   | Поведінка                                                                 | Перевірка           |
| -------------------------- | ------------------------------------------------------------------------- | ------------------- |
| БД недоступна / рестарт    | 503 + `Retry-After: 5`, без деталей; `/health` 200, `/health/ready` 503   | F1–F3, `make chaos` |
| Після підйому БД           | пул перепідключається сам; повтор POST з тим самим ключем → 201, далі 200 | `make chaos`        |
| Deadlock / serialization   | транзакція повторюється цілком ≤ 3 разів з backoff + jitter               | R1–R3               |
| Довгий запит               | `statement_timeout` 5 с → 503                                             | конфіг пулу         |
| Помилка посеред транзакції | `ROLLBACK`, жодного часткового запису (на статиці — відкат снапшота)      | S9                  |

## Відомі обмеження (свідомо відкладено)

- Статус сесії (`open`) читається до блокування. Ендпоінта «закрити сесію» поки немає, тож гонки бути не може;
  коли він з'явиться — перечитувати статус під `FOR UPDATE` (вимога DB-01 це вже покриває).
- Дошка сесії без пагінації: для десятків речей достатньо, виміряємо в Лабі 5.
