# 0004. PostgreSQL 16 + node-postgres (`pg`) з SQL вручну, без ORM

- Статус: accepted
- Дата: 2026-10-20

## Контекст і проблема

Лаба 2 замінює статичні дані реальною БД. Головні вимоги — інваріанти під конкурентними запитами
(I1–I4), ідемпотентний запис і контроль кількості запитів (N+1). Потрібні БД і спосіб доступу до неї.

## Драйвери рішення

- Інваріанти тримаються constraint-ами й блокуваннями: частковий UNIQUE, `FOR UPDATE`, `ON CONFLICT`.
- Кожен SQL-запит видно й можна порахувати (бюджет запитів, DB-04).
- Транзакція — явна, з повтором на deadlock (DB-06).

## Розглянуті варіанти

БД: **PostgreSQL** · SQLite · MongoDB. Доступ: **`pg` + SQL** · Prisma · Drizzle · Kysely · TypeORM.

## Рішення

**PostgreSQL + `pg` з параметризованим SQL у адаптері**, міграції — `.sql` файли зі своїм раннером (~60 рядків).

### Наслідки

- Добре: кожен інваріант — один рядок SQL (`WHERE status = 'in_repair'` в індексі, `ON CONFLICT (idempotency_key)`);
  N+1 знайдено лічильником у `Db.query` — з ORM довелося б вмикати логування й розбирати його.
- Добре: порти з Лаби 1 не змінились по суті — адаптер на БД став поруч зі статичним.
- Погано: маппінг рядків у типи вручну (`toTicket`), немає перевірки SQL типами на етапі компіляції.
- Погано: свій раннер міграцій — без відкату (down). Прийнятно: міграції лише додаються (DB-07).
- Як перевіряємо: `make scenarios-db` (AC6–AC11) на справжньому PostgreSQL; `make n1-report`.

## Плюси і мінуси варіантів

### SQLite

- Добре: без сервера. Погано: немає `SELECT … FOR UPDATE`, один писач — конкурентні сценарії не перевіряються чесно.

### MongoDB

- Добре: гнучка схема. Погано: дані реляційні (тікет ↔ сесія ↔ майстер), інваріант «≤ 1 річ у майстра» — через частковий індекс є, але ліміт черги (I3) потребує транзакцій поверх документів.

### Prisma

- Добре: типізований клієнт, міграції. Погано: `FOR UPDATE` і `ON CONFLICT DO NOTHING` — лише через `$queryRaw`, тобто SQL усе одно вручну; N+1 через `include` легко отримати непомітно; важкий генератор.

### Drizzle / Kysely

- Добре: типізований SQL-білдер, близький до SQL. Найсильніша альтернатива; **переглянемо в Лабі 5**, якщо маппінг вручну стане вузьким місцем. Зараз — додаткова абстракція без потреби.

### TypeORM

- Погано: active record / lazy relations провокують N+1; декоратори змішують домен з ORM — суперечить R2 (`domain-is-pure`).
